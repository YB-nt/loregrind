# Loregrind Eval — 측정 설계

이 프로젝트의 핵심 주장은 "스트립된 바이너리를 리버서처럼 탐색하는 LLM 하네스를 만들었다"가 아니라 **"그리고 그 성능을 측정했다"**이다. 앞부분은 흔하고, 뒷부분이 차별점이다.

**평가는 마지막에 붙이지 않는다.** `docs/PROJECT.md` §6이 "2주차부터 함께 만든다"고 못 박았다. 기능 완성을 기다리지 말고 측정 가능한 지점이 생기는 즉시 지표를 붙인다.

## 합성 정답셋

오픈소스를 컴파일 → 심볼 스트립 → 원본 함수명과 대조.

**난이도 격자**: 컴파일러(GCC / Clang / MSVC) × 최적화(`-O0` ~ `-O3`). 이 격자가 난이도 축이 되고, 결과 표는 셀 단위로 보고한다 — 평균만 내면 `-O0`의 쉬운 성공이 `-O3`의 실패를 가린다.

**보너스**: 동일 소스의 서로 다른 빌드는 **"같은 함수" 정답 쌍**을 무제한 공급한다. 검색 평가(Recall@k)와 리랭커 학습 데이터로 재사용한다. 정답셋을 만들 때 이 쌍을 함께 산출하도록 설계한다 — 나중에 다시 만들려면 전체 빌드를 반복해야 한다.

**실제 멀웨어는 정성 데모용이다.** 정답이 없으므로 정량 지표를 뽑지 않는다. 실 샘플 성능을 숫자로 보고하면 그 숫자에는 근거가 없다.

### 정답 누출 차단 — 먼저 할 일

원본 심볼명이 에이전트가 보는 컨텍스트로 흘러들면 명명 정확도가 통째로 무의미해진다. 누출 경로를 파이프라인 구축 시점에 차단하고, 차단했음을 리포트에 명시한다.

점검할 누출 경로:
- 스트립 후에도 남는 디버그 섹션 / 익스포트 테이블 / RTTI
- PDB 경로 문자열
- 어서션·로그 문자열에 박힌 함수명 (`__func__`, `assert` 매크로 전개)
- 정답셋 파일이 에이전트가 접근 가능한 DB/디렉터리에 있는 경우

마지막 항목이 가장 흔하다. 정답은 에이전트가 읽는 DB와 물리적으로 분리한다.

## 지표

| 지표 | 정의 | 산출 |
|---|---|---|
| 명명 정확도 | 원본 심볼과의 의미 일치율 | 정확 일치 + 의미 동등 판정. 판정 방법(문자열 정규화 / 임베딩 유사도 / LLM 판정)을 리포트에 명시 |
| **환각률** | findings가 인용한 근거가 실제 존재하는가 | **문자열 대조로 자동 검증.** 인용 문자열이 바이너리/DB에 있는지 |
| 탐색 효율 | 핵심 함수 발견까지 읽은 함수 수 / 전체 | "핵심 함수"를 정답셋에서 미리 지정해 둔다 |
| **반대율** | 주입된 사전정보를 에이전트가 뒤집는 비율 | 아래 진단 테스트 참조 |
| 검색 Recall@k / P@1 | 등가 함수를 상위 k에 회수하는가 | 정답 쌍(다른 빌드의 같은 함수)으로 계산 |
| 캐시 히트율·비용 | 코퍼스 성장에 따른 추이 | 단일 값이 아니라 곡선. `runs`의 누적 순서가 x축 |

**환각률은 자동 검증이다.** 모델에게 "네가 환각했니"라고 묻는 방식은 지표가 아니다. findings에 저장된 인용은 원문 그대로여야 이 대조가 성립하므로, 인용이 요약·가공되어 저장되고 있으면 그것 자체를 결함으로 보고한다.

## 어블레이션 (필수 6축)

| 축 | 조건 | 무엇을 보는가 |
|---|---|---|
| 리네임 쓰기 | on / off | 쓰기 도구가 이후 컨텍스트 품질을 올리는가 |
| 탐색 전략 | 랭킹 / 순차 / 랜덤 | L3 랭킹이 값을 하는가 |
| 컨텍스트 구성 | 계층 요약 / 평면 | 요약 카드 가설의 검증 |
| 검증 루프 | on / off | **환각률 변화** — §9~10주차의 핵심 결과 |
| 검색 채널 | 채널별 on/off | 각 채널이 값을 하는가 |
| 코퍼스 상태 | 콜드 / 웜 / **미학습 패밀리 홀드아웃** | 축적이 효과가 있는가, 그리고 과적합이 아닌가 |

**어블레이션은 SQL 한 줄이어야 한다.** 모든 산출물이 `run`에 소속되고 `runs`가 `model`/`prompt_version`/`config`를 기록하기 때문이다(불변식 5).

```sql
SELECT r.config->>'rename_writes' AS cond,
       AVG(m.naming_accuracy), COUNT(*)
FROM run_metrics m JOIN runs r USING (run_id)
GROUP BY cond;
```

SQL로 뽑히지 않으면 **애플리케이션 코드로 우회 집계하지 말고 결함으로 보고한다.** 우회하는 순간 계측 결함이 감춰지고 다음 어블레이션에서 같은 문제가 반복된다.

비교하는 두 run은 대상 축 외의 `model`/`prompt_version`/`config`가 같아야 한다. 다르면 비교가 아니라 착시다.

## 진단 테스트 — 반드시 유지

### 반대율

**반대율이 0에 가까우면 에이전트는 분석이 아니라 복사를 하고 있다.**

일부러 틀린 사전정보를 주입해 에이전트가 뒤집는지 확인한다:
1. 정답셋에서 함수를 고르고, 명백히 틀린 분석 결과를 사전정보로 준비한다 (예: 문자열 비교 함수를 "RC4 복호화"로)
2. 검색 계층이 그것을 반환하도록 주입한다
3. 에이전트가 사전정보를 뒤집고 올바른 결론에 도달하는 비율을 잰다

이 신호는 리포트에서 묻지 않고 전면에 낸다. 사전정보를 결론이 아니라 가설로 제시하는 것(불변식 7)이 지켜지고 있는지를 직접 측정하는 지표이기도 하다.

### 홀드아웃

**홀드아웃 성능이 떨어지면 개선이 아니라 과적합이다.** 콜드 vs 웜과 미학습 패밀리 홀드아웃을 항상 함께 보고한다. 웜 성능만 담은 표는 만들지 않는다.

## 리포트 규율

- 지표에 반드시 `n`을 붙인다. 함수 12개에서 잰 92%는 92%가 아니다.
- 컴파일러×최적화 셀별로 보고한다. 평균은 그다음이다.
- 실패한 어블레이션 셀은 채우지 말고 비워 두고 이유를 적는다.
- **숫자를 좋게 만들지 않는다.** §7은 5주차에 지표가 안 나오면 6주차 이후를 잘라내라고 지시한다 — 그 판단이 가능하려면 숫자가 정직해야 한다.
- 측정하지 못한 것은 "한계 / 미측정"에 남긴다. 정답셋이 없으면 추정하지 말고 "측정 불가"로 보고한다.

## 구현 위치 — 이 규율이 어디에 코드로 박혀 있는가

명세: **`docs/EVAL-SPEC.md`**. 아래 규율을 다시 설계하지 말고 그 문서와 코드를 먼저 읽는다.

| 규율 | 구현 |
|---|---|
| `n` 없는 지표 불가 | `eval/metrics.py:MetricValue`, `run_metrics.n NOT NULL` |
| 측정 불가 ≠ 0% | `MetricValue.unmeasured_reason` (`__post_init__` 이 위반을 거부) |
| 지표 계산에 LLM 금지 | 의미 동등은 정답셋 `aliases` 로 사전 확정 |
| 정답 누출 차단 | `eval/leakage.py` + `make verify-holdout` |
| 어블레이션은 SQL 한 줄 | `Repo.ablation()`, `loregrind eval --ablation-axis` |
| 홀드아웃 열을 지우지 않음 | `eval/report.py:render_metric_table` |
| 지표의 방향 | `eval/metrics.py:LOWER_IS_BETTER` — **한 곳에만 둔다** |

게이트: `make verify`(코드 규율) / `make verify-holdout`(누출·홀드아웃·과적합).
후자는 정답셋이나 홀드아웃 지표가 없으면 **exit 3(미측정)** 으로 실패한다.

## 5주차 컷라인

§7: **5주차 종료 시점에 코어 지표 표가 안 나오면 6주차 이후를 전부 잘라내고 코어를 다듬는 데 남은 시간을 쓴다.** 얕은 5개보다 깊은 2개가 강하다.

평가 담당으로서 이 컷라인의 판정 근거를 제공하는 것이 당신의 일이다. 5주차가 가까워지면 "무엇이 측정되었고 무엇이 안 되었는지"를 명시적으로 보고한다.
