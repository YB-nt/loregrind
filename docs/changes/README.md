# 변경 기록 (docs/changes/)

모든 작업은 여기에 기록을 하나 남긴다.

## 왜 남기는가

`docs/PROJECT.md` §8 산출물 4번은 **"기술 문서 — 설계 결정과 그 근거, 실패한 시도 포함"**을 요구한다. 12주 뒤에 기각한 대안과 실패한 시도를 회상으로 복원하는 것은 불가능하다. 지금 남기는 이 파일들이 최종 기술 문서의 원재료다.

커밋 메시지는 **무엇을 했는지**를 남긴다. 이 문서는 **왜 그렇게 했고, 무엇을 기각했고, 무엇이 아직 검증되지 않았는지**를 남긴다. 둘은 대체 관계가 아니다.

## 파일명

```
docs/changes/YYYY-MM-DD-{slug}.md
```

`{slug}`는 브랜치명의 접미사와 맞춘다 — `feature/l1-string-xrefs` → `2026-08-20-l1-string-xrefs.md`. 브랜치·커밋·문서가 같은 이름으로 묶여야 나중에 되짚을 수 있다.

## 템플릿

```markdown
# {제목}

- **날짜**: YYYY-MM-DD
- **브랜치**: feature/{slug}
- **계층**: L1 / L2 / L3 / L4 / L5 / eval / harness / infra
- **마일스톤**: §7 {N}주차

## 배경
{무엇이 문제였나. 왜 지금 하는가}

## 변경 내용
| 파일 | 변경 | 신규/수정/삭제 |

## 설계 결정과 근거
{채택한 방식과 그 이유}

## 기각한 대안
| 대안 | 기각 사유 |
{없으면 "해당 없음". 있는데 안 적으면 §8 산출물이 비어간다}

## 불변식·안전 규칙 영향
| 항목 | 영향 | 판정 |
{§11 불변식 중 관련 항목, §10 안전 규칙 중 관련 항목만. 무관하면 생략}

## 검증
- ruff / mypy / pytest 결과
- 감사 결과: PASS n / FAIL n / UNKNOWN n
- **미검증 항목과 그 이유** (외부 도구 부재 등)

## 미해결 / 후속
{알려진 한계, 다음에 할 일}
```

## 규칙

- **검증하지 않은 것을 검증했다고 쓰지 않는다.** Ghidra·capa·Unicorn 부재로 실행 검증을 못 했으면 "미검증 — {도구} 부재"로 남긴다. 이 프로젝트가 측정하려는 것이 환각률인데 기록이 환각이면 곤란하다.
- **기각한 대안을 비워두지 않는다.** 정말 대안을 검토하지 않았다면 그것 자체가 신호다.
- **실패한 시도도 기록한다.** 되돌린 작업, 성능이 안 나온 접근, 틀린 가설 — §8이 명시적으로 요구하는 항목이다.
- 기록은 작업과 같은 커밋에 넣는다. 나중에 몰아서 쓰면 이유가 이미 증발해 있다.
