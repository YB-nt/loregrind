# 정답셋 코퍼스 소스 — 측정보다 먼저 커밋되는 것 (§6)

- **날짜**: 2026-08-18
- **브랜치**: feature/groundtruth
- **계층**: eval
- **마일스톤**: §7 5주차 컷라인의 전제 (3·4주차 완료 기준도 여기 걸려 있다)

## 배경

3주차까지 코드는 섰지만 **완료 기준이 전부 미달**이다. 이유가 하나다 — 정답셋이
없다. `naming_accuracy`·`exploration_efficiency`·`contradiction_rate`·`recall_at_k`
넷이 전부 정답셋을 입력으로 받는다. `EVAL-SPEC.md` §2 는 스키마만 정의했고 격자를
돌리는 코드는 없었다.

이 커밋은 그 파이프라인의 **입력**을 만든다.

## 변경 내용

| 파일 | 변경 | 신규/수정 |
|---|---|---|
| `eval/corpus/sources/cryptolite.c` | 정답이 있는 리버싱 대상 8함수 | 신규 |
| `eval/corpus/sources/cryptolite.annotations.json` | `is_key_function` / `aliases` / `wrong_prior` | 신규 |

## 설계 결정과 근거

### 1. 주석 파일이 **측정보다 먼저** 커밋된다

`is_key_function` 은 §6 탐색 효율의 분자 기준이고, `aliases` 는 명명 정확도의
동등 판정이며, `wrong_prior` 는 반대율 진단에 주입할 틀린 사전정보다. 셋 다
자동으로 유도할 수 없다.

`EVAL-SPEC.md` §2 가 "**사후에 정하면 지표를 유리하게 조작할 수 있다**"고 못 박은
항목이므로, 소스와 같은 커밋에 넣어 **어떤 측정보다 앞선 시점에 고정**한다.
빌드 스크립트가 이 값을 지어내지 않는다 — 주석에 없는 함수는 주석 없이 들어간다.

### 2. 함수는 "의사코드만 보고 이름을 맞힐 수 있을 만큼" 특징적이어야 한다

그렇지 않으면 명명 정확도가 재는 것이 시스템 성능이 아니라 **문제의 모호함**이
된다. 그래서 지문이 뚜렷한 것들을 골랐다 — RC4 의 256바이트 S-box 와 KSA 치환,
FNV-1a 의 `0x811C9DC5`/`0x01000193`, djb2 의 `5381`·`hash*33`, Base64 알파벳 문자열.
§5 가 "희귀 32비트 상수는 거의 고유 식별자"라고 한 그 상수들이다.

동시에 **혼동쌍**을 일부러 넣었다: `xor_decode` ↔ `checksum_buffer`(루프 형태가
비슷하다), `rc4_crypt` ↔ `xor_decode`(둘 다 XOR 이다), `base64_encode` ↔
`hex_encode`(wrong_prior). 전부 맞히기 쉬운 문제만 넣으면 정확도가 100% 에 붙어
변별력이 사라진다.

### 3. `NOINLINE` — 정답 함수가 사라지지 않게

`-O2`/`-O3` 셀에서 컴파일러가 인라인해 버리면 정답 함수가 통째로 없어지고,
그 셀의 `n` 이 조용히 줄어든다. 격자의 난이도 축이 "최적화 강도"여야 하는데
"함수가 남았는가"가 되어 버린다.

### 4. 순수 계산만 — 실행 대상이 아니다

파일·레지스트리·네트워크를 건드리지 않는다. 코퍼스는 컴파일 대상일 뿐이고 어떤
경우에도 실행되지 않는다 (§10). 함수 이름은 리버싱 대상으로서 현실적이되, 동작은
전부 순수 계산이다.

### 5. 소스는 커밋하고 바이너리는 커밋하지 않는다

`.c` 와 주석은 텍스트이고 정답의 근거이므로 커밋한다. 빌드 산출물은
`artifacts/` (gitignore 대상)로 나간다 — §10 의 "평문 PE 를 커밋하지 않는다"는
멀웨어만의 규칙이 아니라 저장소에 바이너리를 넣지 않는다는 규칙이다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 실제 오픈소스(zlib·mbedtls)를 통째로 빌드 | 빌드 시스템·의존성이 딸려 오고, 함수 수천 개 중 무엇이 핵심인지 주석을 달 수 없다. 주석 없는 정답셋은 탐색 효율·반대율을 못 잰다 |
| `is_key_function` 을 복잡도·API 로 자동 유도 | 그것이 바로 랭킹 신호다. 랭킹이 고른 함수를 정답으로 삼으면 탐색 효율이 자기 채점이 된다 |
| 주석을 생성 시점에 만들기 | 사후 지정 = 지표 조작 여지 (§2가 금지) |
| `NOINLINE` 없이 자연스럽게 | -O2 이상에서 정답 함수가 사라져 격자 셀의 n 이 조용히 줄어든다 |
| 헷갈릴 여지 없는 함수만 | 정확도가 100% 에 붙어 변별력이 사라진다 |

## 검증

```
clang -O0 -c cryptolite.c → nm
  _rc4_init _rc4_crypt _xor_decode _fnv1a_hash _djb2_hash
  _base64_encode _checksum_buffer _decode_config_blob _main
  → 주석 8함수가 전부 심볼로 남는다 (NOINLINE 확인)

주석: 8함수 / 핵심 5개
make verify → PASS (180 passed)
```

### 미검증 항목

| 항목 | 이유 |
|---|---|
| **PE 빌드** | **이 기계에 PE 툴체인이 없다.** Apple clang 만 있고 mingw-w64·zig·MSVC 가 없어 Mach-O 만 나온다. §2 범위는 PE 전용이므로 **이 코퍼스로 실제 격자를 만들 수 없다** |
| 컴파일러 격자 (gcc/clang/msvc × -O0~-O3) | 위와 같은 이유. `-O0` Mach-O 한 셀만 컴파일 확인했다 |
| 최적화 단계에서 함수 생존 | `-O0` 에서만 확인했다. `-O2`/`-O3` 에서 `NOINLINE` 이 실제로 버티는지는 미확인 |
| 문제 난이도가 적절한가 | 사람이 의사코드로 맞힐 수 있는지 실측하지 않았다. 정확도가 바닥이면 문제가 어려운 것인지 시스템이 나쁜 것인지 구별되지 않는다 |

## 미해결 / 후속

이 커밋은 파이프라인의 **입력**만 만든다. 남은 것:

1. `eval/corpus/toolchain.py` — 컴파일러 탐지. **PE 를 못 만드는 툴체인이면 거부해야
   한다** (Mach-O 코퍼스를 조용히 만들면 §2 범위 위반이자 무의미한 숫자가 된다)
2. `eval/corpus/build.py` — 컴파일러 × 최적화 격자 → `artifacts/corpus/`
3. `eval/corpus/symbols.py` — `nm` → `{addr: symbol}`. 스트립은 코드를 옮기지 않으므로
   언스트립 빌드의 주소가 스트립 빌드에서도 유효하다 (이것이 정답 주소의 근거다)
4. `eval/corpus/generate.py` — `groundtruth.json` 조립 + `pairs` 산출.
   `EVAL-SPEC.md` §2 는 pairs 를 **생성 시점에 함께** 만들라고 요구한다 — 나중에
   만들려면 전체 빌드를 반복해야 한다

**PE 툴체인(mingw-w64 등) 설치가 선행 조건이다.** 없으면 2~4를 써도 코퍼스가 안 나온다.

이 브랜치는 사용자 요청에 따라 **`develop`에 병합하지 않고 푸시만 한다.**
