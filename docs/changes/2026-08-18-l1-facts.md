# L1 확장 — 문자열·임포트·API 호출 추출 (마이그레이션 `0002`)

- **날짜**: 2026-08-18
- **브랜치**: feature/l1-facts (feature/spec 에서 분기)
- **계층**: L1 + DB
- **마일스톤**: §7 2주차의 전제 (`docs/SPEC.md` §3)

## 배경

L2 도구 `search_strings` / `get_apis_used`가 요구하는 사실이 DB에 없었다. 1주차는
`functions`와 `call_edges`만 적재한다.

미루면 안 되는 이유는 순서가 아니라 **비용**이다. 같은 사실을 L3 랭킹 신호(의심 API
클러스터, 고신호 문자열 참조)와 §5 BM25 토큰 스트림이 다시 요구하므로, 나중에
추가하면 `analyzeHeadless`를 두 번 돌려야 한다. 대형 바이너리에서 이 비용이 가장 크다.

## 설계 결정과 근거

### 1. 문자열·임포트를 함수와 같은 Ghidra 패스에서 뽑는다

`-postScript`를 두 개 걸거나 `analyzeHeadless`를 두 번 돌리는 대신
`export_functions.py` 하나가 세 파일을 쓴다. 프로그램을 다시 여는 비용이 대형
바이너리에서 그대로 분석 시간이 된다. `scripts/` ↔ `src/` 경계(파일만 넘는다)는
그대로다 — 파일이 하나에서 셋으로 늘었을 뿐이다.

### 2. `imports`의 UNIQUE 키에서 `ordinal`을 뺐다 (**사양 정정**)

`SPEC.md` §3은 `UNIQUE (binary_id, module, api_name, ordinal)`로 적혀 있었다.
**SQLite는 UNIQUE 안의 NULL을 서로 다른 값으로 취급하므로**, 이름 임포트(대다수,
`ordinal IS NULL`)의 중복을 이 키가 전혀 잡지 못한다. 서수 전용 임포트는 Ghidra가
`Ordinal_5` 형태의 이름을 주므로 `(module, api_name)`만으로 유일하다.
사양을 고치고 구현을 맞췄다.

### 3. `strings.truncated` 컬럼을 추가했다 (**사양 정정**)

문자열 하나가 4096자를 넘으면 자르는데, 자른 사실을 남기지 않으면 적재 후에 손실
여부를 알 방법이 없다. `length`는 잘리기 전 원본 길이를 유지한다. 도구 응답의
`truncated` 플래그(§4.2)와 같은 규율이다 — **조용히 자르지 않는다.**

### 4. `meta.json`의 새 카운트는 없음과 0을 구별한다 (`int | None`)

v1 산출물에 대해 `string_count=0`으로 채우면 "문자열이 없는 바이너리"와 "문자열을
추출하지 않았다"가 같아진다. `None`으로 두고, v1 적재 시 `LoadResult.warnings`에
`NOT_EXTRACTED`를 남긴다. `EVAL-SPEC.md`의 "측정 불가는 0%가 아니다"를 적재 계층에
그대로 적용한 것이다.

### 5. `search_strings`는 LIKE 와일드카드를 이스케이프한다

사용자 입력의 `%` `_`가 와일드카드로 작동하면 **질의 표현력이 가변**이 되고, §6 탐색
효율을 run 사이에서 비교할 수 없다. 이스케이프 순서(역슬래시 먼저)도 테스트로 고정했다.

### 6. `insert_imports`가 `(module, api_name) → import_id` 지도를 반환한다

`api_calls`가 `import_id`를 참조하므로 적재 순서가 강제된다. 지도를 반환하지 않으면
호출부가 다시 SELECT 해야 하고, **그 SELECT가 `repo` 밖으로 새어 나간다** — DB 접근이
`repo.py` 하나를 지난다는 규율이 거기서 깨진다.

### 7. 중복 주소·중복 임포트를 `IntegrityError` 전에 잡는다

어느 주소가 중복인지 알려주는 편이 SQLite의 UNIQUE 위반 메시지보다 낫다. 추출
스크립트의 버그를 디버깅할 때 이 차이가 크다.

### 8. 참조가 없는 문자열도 남긴다

버리면 "참조를 못 찾았다"와 "참조가 없다"를 적재 단계에서 구별할 수 없다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 별도 스크립트 `export_strings.py` + 두 번째 `-postScript` | 프로그램을 다시 여는 비용. 대형 바이너리에서 분석 시간 증가 |
| 문자열을 `functions.jsonl`의 함수 레코드에 인라인 | 참조가 없는 문자열을 표현할 수 없고, 같은 문자열이 함수 수만큼 중복된다 |
| `api_calls`에 `import_id` 대신 `(module, api_name)` 직접 저장 | 임포트 메타(iat_addr, ordinal)가 호출 수만큼 중복. 모듈명 정규화가 두 곳으로 갈라진다 |
| v1 산출물 적재 거부 | 이미 적재한 코퍼스를 재추출해야 한다. 경고 + `NOT_EXTRACTED`로 충분하다 |
| `string_count` 등을 0 기본값으로 | 없음과 0이 같아진다 (위 §4) |
| 문자열 상한 없이 전량 저장 | 정의된 데이터 크기에 상한이 없다. 4096자 + `truncated` 플래그로 절충 |
| `search_strings` 정규식 지원 | ReDoS + 질의 표현력 가변 (`SPEC.md` §4.2에서 이미 기각) |

### 미검증 항목

| 항목 | 이유 |
|---|---|
| **`scripts/export_functions.py`의 새 코드 전체** | **Ghidra 미설치. 한 줄도 실행되지 않았다.** `hasStringValue()`, `getDefinedData(True)`, `getExternalSymbols()`, `getReferencesTo()` 의 시그니처와 반환형이 Ghidra 11.x 에서 맞는지 확인되지 않았다 |
| Jython 2.7 의 `unicode()` 분기 | Py3 에서는 `NameError` → `str()` 로 떨어지게 썼으나 Jython 쪽 경로는 미실행 |
| 인코딩 판정 (`string_encoding`) | 데이터 타입 이름 문자열 매칭이다. 실제 Ghidra 타입 이름 목록으로 검증하지 않았다 — 그래서 알 수 없는 값은 `other` 로 접는다 |
| 서수 전용 임포트 (`Ordinal_5`) | Ghidra가 실제로 그 이름을 주는지 미확인. UNIQUE 키 설계가 여기에 의존한다 |
| 실제 바이너리의 문자열 규모 | 합성 2건으로만 확인. 수만 건에서 `_read_jsonl` 이 전량을 메모리에 올린다 |
| `iat_addr` 의미 | 외부 심볼 주소를 그대로 넣었다. Ghidra 에서 이것이 IAT 엔트리 주소인지 thunk 주소인지 미확인 |

  (기존 `insert_functions` 의 같은 한계와 함께).

  (`docs/SPEC.md` §4·§5·§6).
- 이 브랜치는 사용자 요청에 따라 **`develop`에 병합하지 않고 푸시만 한다.**
