- **날짜**: 2026-08-17
- **브랜치**: `feature/l1-extract`
- **계층**: L1 / db
- **마일스톤**: §7 1주차 — 완료 기준 "SQL로 직접 질의 가능"

## 배경

사양·하네스·레이아웃은 있었지만 구현 코드가 0행이었다. 1주차 목표는 스트립된 바이너리
하나를 Ghidra 로 추출해 DB 에 넣고 SQL 로 질의 가능하게 만드는 것이다.

이 단계에서 정하는 스키마가 이후 모든 계층의 제약이 된다. 특히 `run_id`와
`superseded_by`를 지금 느슨하게 두면 §6 평가 설계가 4주 뒤에 무너진다.

### ruff 가 문서를 고쳐 쓰던 문제

`uv run ruff format .` 이 **마크다운 안의 Python 코드 블록까지 포맷했다.**
`.claude/skills/loregrind-implementation/SKILL.md` 의 예시 코드가 조용히 바뀌어 있었다
(줄바꿈 병합, 빈 줄 삽입). 되돌리고 `extend-exclude` 에 `*.md` 를 넣었다.

스킬·문서의 예시 코드는 "이렇게 쓰라"는 설명이고 줄바꿈 위치 자체가 설명의 일부다.
포매터가 이것을 건드리면 하네스 문서가 커밋마다 흔들린다.

## 설계 결정과 근거

### append-only 를 DB 트리거로 강제했다

문서와 `repo.py` 만으로는 우회 경로가 생긴다(교훈: `docs/LEARNING.md` §3-2). `schema.sql` 에
트리거 5개를 두어 **DB 가 직접 거부**하게 했다.

- `trg_function_analyses_append_only` — 판단 필드(`proposed_name`, `summary`,
  `confidence`, `evidence_json`, `source`, `code_hash`)의 UPDATE 를 ABORT
- `trg_function_analyses_supersede_once` — 이미 가려진 행을 다시 가리는 것을 ABORT
- `trg_function_analyses_no_delete` / `trg_hypotheses_no_delete` — DELETE 를 ABORT
- `trg_hypotheses_append_only` — 상태 전이(`open`→`confirmed`)를 UPDATE 로 하는 것을 ABORT

**허용되는 UPDATE 는 `superseded_by` 링크 부착 하나뿐이다.** 판단 내용의 변경이 아니라
"이 행은 가려졌다"는 표시이기 때문이다. 트리거의 `WHEN` 절이 그 예외를 정확히 표현한다.

`tests/db/test_repo.py` 는 `repo` 를 **우회해서** 직접 UPDATE/DELETE 를 시도하고
`sqlite3.IntegrityError` 가 나는지 확인한다. 통과를 확인하는 것이 아니라
**위반이 거부되는지**를 확인한다.

### `run_id` 를 NOT NULL + FK 로 못박았다

`function_analyses.run_id` 와 `hypotheses.run_id` 가 `NOT NULL REFERENCES runs(run_id)` 다.
존재하지 않는 run 으로 판단을 넣으면 INSERT 가 실패한다. 이것이 §6 어블레이션이
SQL 한 줄이 되는 전제다.

### `function_id` FK — §4 의 `addr` 표기에서 벗어났다

§4 주요 테이블은 `function_analyses`에 `addr`을 적었지만 `function_id INTEGER REFERENCES
functions(id)` 를 썼다. 이유 두 가지: ① 바이너리가 다르면 같은 주소가 충돌한다
② 존재하지 않는 함수에 대한 판단을 막을 수 없다. `addr`은 `v_current_analyses` 뷰가
조인해서 제공하므로 조회 편의는 잃지 않는다.

### 조회 필터를 뷰와 `repo.py` 안에 넣었다

`v_current_analyses` / `v_current_hypotheses` 가 `superseded_by IS NULL` 을 품고 있고,
`repo.current_analysis()` 는 그 뷰만 읽는다. 호출부가 필터를 잊을 수 없다.

### `config` 를 `create_run` 안에서 자동 마스킹한다

`redact_config()` 가 키 이름에 `key`/`token`/`secret`/`password`/`credential` 이 들어간 값을
`<redacted>` 로 바꾼다. 호출자가 잊어도 API 키가 DB 에 남지 않는다(§10). **키 이름 기반이라
완벽하지 않다** — 1차 방어는 애초에 설정 객체에 키를 담지 않는 것이고 이건 2차 방어다.

### 성공 판정을 종료 코드에 위임하지 않았다

`verify_log()` 가 로그에서 `ERROR|Script failed|OutOfMemory` 를 찾는다. OOM 은 로그에만
남고 종료 코드는 0 이다. 추가로 `loader.py` 가 `meta.json` 의 `function_count` /
`decompile_failure_count` 를 실제 레코드 수와 대조해 어긋나면 적재를 거부한다.

### 디컴파일 실패는 해시를 만들지 않는다

`code_hash(None)` 과 `code_hash("")` 는 `None` 이다. 빈 문자열의 해시는 모든 실패 함수에서
동일해서, 서로 무관한 함수들이 "같은 코드"로 뭉쳐버린다.

### 정규화 규칙에 버전을 붙였다

`NORMALIZE_VERSION` 이 해시 입력에 들어간다. 규칙을 바꾸면 해시가 전부 달라지므로
낡은 해시를 새 규칙 결과와 비교하는 사고를 막는다. 테스트가 이 성질을 고정한다.

### CLI 는 `extract` 와 `load` 를 분리했다

한 명령으로 묶으면 Ghidra 재실행 없이 적재만 다시 할 수 없다. 추출은 분 단위, 적재는
초 단위다. 스키마를 고치는 동안 추출을 반복하고 싶지 않다.

### 미구현 서브커맨드는 exit code 2 로 거부한다

`analyze` / `eval` 이 조용히 아무것도 하지 않으면 "돌았는데 결과가 없다"는 오해를 만든다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| `superseded_by` 대신 `supersedes`(새 행이 이전 행을 가리킴) | UPDATE 를 완전히 없앨 수 있지만 "현재 유효한 행" 조회가 NOT EXISTS 서브쿼리가 된다. 조회가 압도적으로 잦으므로 링크 부착 1회 UPDATE 를 택했다. `/db-change` 가 이 예외를 명시적으로 허용한다 |
| append-only 를 `repo.py` 에서만 강제 | 우회 경로가 생긴다. 트리거가 마지막 방어선이다 |
| `addr` 을 INTEGER 로 저장 | 추출 사실을 원형으로 보존하지 못한다. Ghidra 출력과 문자열 비교가 안 되면 재현성 확인이 번거로워진다 |
| `functions` 에 `callees` 를 JSON 컬럼으로 | 콜 그래프 역방향 질의(`get_callers`)가 전체 스캔이 된다. §4 무효화 역전파가 이 질의에 의존한다 |
| 추출과 적재를 한 명령으로 | 위 "CLI 분리" 참조 |
| Ghidra 스크립트를 PyGhidra(Python 3)로 | `/ghidra-extract` 가 "실행 경로는 하나만 — `analyzeHeadless -postScript`"를 못박았다. 두 경로는 심볼 해석과 디컴파일러 옵션이 달라 결과가 재현되지 않는다 |
| 마이그레이션 `0001` 로 기반 스키마 작성 | `schema.sql` 과 내용이 중복돼 DDL 소스가 둘이 된다. 기반은 `schema.sql`, 마이그레이션은 그 이후의 변경부터 |
| `strings` / `imports` 테이블을 지금 추가 | 1주차 범위를 넘는다. `/ghidra-extract` 의 JSONL 계약(함수 단위)에 없는 것을 추측으로 넣지 않았다 |

### 미검증 — 이것이 이번 작업의 가장 큰 구멍이다

| 항목 | 이유 |
|---|---|
| `scripts/export_functions.py` **전체** | **Ghidra 미설치.** 한 줄도 실행되지 않았다. Ghidra API 시그니처(`getPrototypeString`, `CyclomaticComplexity` 임포트 경로, `getGhidraVersion`)가 11.x 에서 맞는지 확인되지 않았다 |
| `runner.py` 의 `analyzeHeadless` 호출 | 같은 이유. 명령 조립은 `/ghidra-extract` 정규 형태를 따랐지만 실행 완주는 미확인 |
| 실제 바이너리에서의 정규화 품질 | 합성 코드 2개로만 확인했다. 실제 디컴파일 출력에는 `CONCAT44`, `SUB84`, `__thiscall` 등이 섞이고 규칙이 과하거나 부족할 수 있다 |
| 대형 바이너리 성능 | 함수 2개로 확인했다. 수천 개일 때 `insert_functions` 의 메모리(전체 리스트를 만든다)가 문제될 수 있다 |

`without_code_hash` 카운터를 적재 결과에 넣은 것이 세 번째 항목의 조기 경보다 —
0 이 아니면 정규화가 코드를 통째로 지운 것이다.

## 미해결 / 후속

- **Ghidra 실측 1회가 다음 작업의 전제다.** `analyzeHeadless -help` 로 플래그를 확인하고
  작은 샘플로 완주시킨 뒤 `runner.py` 의 힙·`-max-cpu` 와 `export_functions.py` 의 API
  호출을 실측값으로 고친다. 그전까지 이 두 파일은 "확정"이 아니다
- `insert_functions` 를 배치 단위 스트리밍으로 바꿀지 검토 (대형 바이너리)
- `.env.example` 여전히 없음
- `docs/ablation.md` 여전히 없음
- 2주차 L2 에서 **프롬프트 인젝션 격리**를 실제로 구현해야 한다. 지금은 격리해야 할
  프롬프트 조립 코드 자체가 없어서 유보 상태다
