# 구현 사양서 `docs/SPEC.md` 신설 — 인터페이스 계약을 코드 앞에 고정

- **날짜**: 2026-08-18
- **브랜치**: feature/spec
- **계층**: 전체 (L1 확장 · L2 · L3 · L4 · 검색 · L5)
- **마일스톤**: §7 2주차 착수 전 사양 확정

## 배경

1주차(L1)와 평가 하네스 뼈대가 끝난 시점에서, 다음 작업인 §7 2주차(L2 도구 층 +
읽기 전용 에이전트)를 시작하려면 **아직 아무 데도 적혀 있지 않은 결정**이 최소 여섯
개 필요했다.

- MCP 도구의 정확한 시그니처와 응답 형식
- 바이너리 유래 텍스트를 어디서 격리하는가 (도구 층인가 프롬프트 조립 지점인가)
- 예산 게이트의 단위와 초과 시 동작
- `search_strings` / `get_apis_used`가 요구하는 사실이 **DB에 없다**는 사실의 처리
- 쓰기 도구를 어블레이션 1축과 어떻게 연결하는가
- 각 주차의 완료를 무엇으로 판정하는가

`PROJECT.md`는 무엇을 왜 만드는지를 정하지만 이 수준의 계약을 담지 않는다(담아서도
안 된다 — 요청서가 구현 세부로 오염되면 권위가 흐려진다). 계약을 적지 않은 채
구현에 들어가면 구현자가 즉석에서 정하고, **다음 계층이 다르게 가정한다.**

## 설계 결정과 근거

### 1. 문서를 새로 만들되 `PROJECT.md`를 고치지 않았다

`PROJECT.md`는 요청서다. 도구 응답 JSON 형식이 거기 들어가면 "사양이 어긋나면
`PROJECT.md`가 이긴다"는 규칙이 작동하지 않게 된다 — 구현 세부가 바뀔 때마다
최상위 권위 문서를 고쳐야 하기 때문이다. 권위 사슬을
`PROJECT.md > SPEC.md > 코드`로 3단으로 만들고, `EVAL-SPEC.md`를 `SPEC.md`와 동급의
하위 사양으로 놓았다.

### 2. L1 확장(문자열·임포트)을 2주차의 **전제**로 끌어올렸다

L2의 `search_strings` / `get_apis_used`가 요구하는 사실이 지금 DB에 없다. 이것을
"도구를 만들 때 같이 하자"로 미루면 안 되는 이유는 순서가 아니라 **비용**이다 —
같은 사실을 L3 랭킹 신호와 §5 BM25 토큰 스트림이 다시 요구하므로, 나중에 추가하면
추출을 두 번 돌려야 하고 대형 바이너리에서 그 비용이 가장 크다.
마이그레이션 `0002`로 `strings` / `string_xrefs` / `imports` / `api_calls` 4테이블,
`extract_schema_version` 1 → 2.

### 3. `NOT_EXTRACTED`를 빈 결과와 구별했다

version 1 산출물에 대해 `search_strings`가 빈 배열을 반환하면 에이전트는 "문자열이
없는 바이너리"로 읽는다. **측정 불가는 0이 아니다** — `EVAL-SPEC.md`가 지표에
적용한 규율을 도구 응답에도 그대로 적용했다.

### 4. 격리는 프롬프트 조립 지점 **한 곳**에서만 한다

도구 층에서도 감싸면 이중 이스케이프된다. 도구는 원문을 반환하고
`analyze/context.py`의 `wrap_untrusted`가 유일한 격리 지점이다. 대신 §4.1에
"바이너리 유래 텍스트 목록"을 명시해 감사가 누락을 잡을 수 있게 했다.

### 5. 바이너리를 서버 시작 시 고정하고 도구 인자에서 뺐다

`binary_id`를 인자로 받으면 (a) 에이전트가 다른 샘플을 헤집는 경로가 열리고,
(b) run 하나가 바이너리 하나에 대응하지 않게 되어 §6 어블레이션의 귀속이 복잡해진다.

### 6. `evidence`를 `{kind, ref}` 구조로 고정했다

§6 환각률은 "findings가 인용한 근거가 실제 존재하는가"를 **문자열 대조로 자동
검증**한다. `evidence`가 자유 텍스트면 이 검증이 불가능하고, 그러면 §8 핵심 주장의
절반("그 성능을 측정했다")이 사라진다. 지표가 데이터 구조를 결정한 사례다.

### 7. `functions.is_library`를 파생 캐시로 재정의했다

스키마는 "L3 필터가 채운다"고만 적혀 있어 추출 사실 테이블을 근거 없이 UPDATE하는
경로가 열려 있었다. `library_verdicts`(run_id 포함, append-only)에 판정과 방법·버전을
남기고 컬럼은 재계산 가능한 캐시로 다루도록 규정했다.

### 8. 완료 판정을 문장이 아니라 명령으로 적었다

§7 마일스톤의 완료 기준("함수 1개를 제대로 요약")은 판정자에 따라 갈린다.
§12에 주차별 **실행 명령과 기대 결과**를 넣었다. 3주차 판정이
`make ablation`의 두 조건 행이 각각 `n>0`인 것이라면, 그것은 다투어질 수 없다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| `PROJECT.md`에 도구 사양을 직접 추가 | 요청서가 구현 세부로 오염되면 "어긋나면 PROJECT.md가 이긴다"가 작동하지 않는다 |
| 계층별로 `SPEC-L2.md`, `SPEC-L3.md` 분할 | 경계면 계약(§2)이 문서 사이로 흩어진다. 경계면이야말로 가장 자주 깨지는 지점이므로 한 곳에 있어야 한다 |
| 2주차 사양만 쓰고 나머지는 나중에 | L3~L5의 요구가 2주차 결정을 이미 구속하고 있었다 (evidence 구조, strategy 인자, 격리 지점). 뒤를 안 보고 앞을 정하면 두 번 고친다 |
| MCP에 `query(sql)` 노출 | 에이전트 행동 귀속 불가 → 어블레이션 전체 무의미 |
| 도구 인자로 `binary_id` 받기 | 위 §5 |
| `search_strings` 정규식 지원 | ReDoS 표면 + 질의 표현력 가변이면 탐색 효율 비교 불가 |
| 문자열·임포트 추출을 L3 착수 시점으로 미룸 | 추출 2회. 대형 바이너리에서 최대 비용 |
| `evidence` 자유 텍스트 | 위 §6 |
| 도구 층 격리 | 위 §4 (이중 이스케이프) |
| 검색 채널 점수 가중합 | 스케일 지배 → 채널 어블레이션 해석 불가. §9가 이미 기각한 선택지 |

### 미검증 항목

| 항목 | 이유 |
|---|---|
| §3의 Ghidra 측 추출 인터페이스 (`strings.jsonl` / `imports.jsonl`) | **Ghidra 미설치.** `getSymbolTable`·`getReferenceManager` API 시그니처가 11.x에서 맞는지 확인되지 않았다. 구현 전 실측 1회가 필요하다 |
