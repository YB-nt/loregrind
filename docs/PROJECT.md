# Loregrind — 프로젝트 요청서

> **Loregrind — An Agentic Reverse Engineering Knowledge Base**
> 스트립된 바이너리를 리버서처럼 탐색하고, 분석할수록 더 싸고 정확해지는 에이전트 하네스.

이 문서는 **무엇을 만드는가**를 정의한다.
작업 규칙과 금지사항은 `CLAUDE.md`를 따른다.

---

## 1. 문제 정의

스트립된 바이너리는 이름 없는 함수 수천 개와 타입 없는 변수의 덩어리다.
인간 리버서는 이것을 **전부 읽지 않는다.** 문자열과 임포트를 보고 몇 개를 찍어
진입하고, 호출 관계를 타고 이동하며, 파악한 함수에 이름을 붙여
다음에 읽을 코드를 읽기 쉽게 만든다.

따라서 이것은 **요약 문제가 아니라 탐색과 컨텍스트 압축 문제다.**
"디컴파일 코드를 LLM에 요약시키는" 접근은 이 프로젝트의 실패 모드다.

두 번째 문제: LLM은 **읽고 추측할 뿐 검증하지 않는다.**
"이건 RC4 복호화 같다"고 말할 뿐 그것이 맞는지 확인할 수단이 없다.

세 번째 문제: 매 분석이 **처음부터 다시 시작된다.**
같은 라이브러리 함수, 같은 암호 루틴을 매번 새로 읽는다.

Loregrind는 이 셋을 각각 **탐색 계층**, **검증 루프**, **지식 축적**으로 푼다.

---

## 2. 범위

### 포함
- x86/x64 PE 바이너리 정적 분석 (Ghidra 기반)
- 함수 단위 격리 에뮬레이션을 통한 가설 검증
- 분석 결과의 영속 저장과 하이브리드 검색 기반 재사용
- 정량 평가 스위트와 어블레이션

### 제외 (명시적으로 다루지 않음)
- **언패킹** — 입력은 언패킹된 바이너리를 전제한다
- **전체 샘플 실행** — 어떤 형태의 동적 실행도 하지 않는다
- ELF / Mach-O — 구조는 확장 가능하게 두되 구현하지 않는다
- 실시간 서비스, 웹 UI, 멀티 유저

범위를 넓히지 않는 것이 이 프로젝트의 최우선 규율이다.
"범용 시스템"은 실패 모드다.

## 3. 아키텍처

5계층으로 분리한다.

### L1. 추출 (Ghidra headless)
`analyzeHeadless` + PyGhidra 스크립트로 정적 사실을 일괄 추출해 DB에 적재.
함수 목록, 콜 그래프, xref, 디컴파일 C, 문자열, 임포트, 데이터 타입.

**추출은 에이전트 런타임과 분리된다.** 에이전트는 따뜻한 인덱스에만 질의하며
런타임에 Ghidra를 호출하지 않는다.

### L2. 도구 (MCP 서버)
좁고 명확한 도구만 노출한다. 만능 도구와 raw SQL은 금지.

```
list_candidates(strategy, limit)    get_function(addr)
get_callers/get_callees(addr)       search_strings(pattern)
get_apis_used(addr)                 get_known_analysis(addr)
rename_function(addr, name)         set_comment(addr, text)
record_analysis(...)                record_finding(...)
emulate_function(addr, args)        record_hypothesis(...)
```

**쓰기 도구가 핵심이다.** 리네임이 이후 디컴파일 결과에 전파되어
에이전트 자신의 작업이 이후 컨텍스트 품질을 끌어올린다.

### L3. 우선순위 (탐색)
수천 개를 다 읽을 수 없으므로 순서를 정한다. 신호:
의심 API 클러스터, 고신호 문자열 참조, capa 결과 매핑,
콜 그래프 위치(도달 깊이·fan-in/out), 복잡도 이상치.

**랭킹은 결정론적 코드가 한다.** LLM은 무엇을 읽을지 고르지 않고,
상위 N개를 읽고 무엇을 할지만 결정한다.

이 계층 앞단에 **라이브러리 함수 필터**(FID/시그니처)를 둔다.
분석 대상을 절반 이하로 줄이는, 단일 최대 효과의 최적화다.

### L4. 분석 루프
- **바텀업**: 말단 함수부터 명명하고 올라간다
- **요약 카드**: 상위 함수 컨텍스트에는 하위 함수의 원시 코드가 아니라 압축 카드가 들어간다
- **서브에이전트**: 콜 그래프 서브트리를 위임하고 카드 하나만 회수한다
- **검증**: 가설을 세우면 에뮬레이션으로 실험해 확정하거나 폐기한다
- **예산**: 함수당 토큰 상한, run당 비용 상한을 코드에 하드코딩
- **모델 계층화**: 재검증은 저가 모델, 신규 상위 함수는 강한 모델

### L5. 산출물
주석·리네임이 적용된 Ghidra 프로젝트, 근거 인용이 붙은 findings,
ATT&CK 매핑, IOC 목록, 마크다운 리포트.

## 4. 데이터 모델

### 원칙
1. **추출 사실은 불변, 에이전트 판단은 append-only.**
   UPDATE 하지 않는다. 새 행 + 이전 행의 `superseded_by`.
2. **모든 산출물은 `run`에 소속된다.** `model`, `prompt_version`, `config`가
   행마다 추적되어야 어블레이션이 SQL 한 줄이 된다.
3. **DB가 단일 진실 소스.** Ghidra에는 단방향 apply만 한다.
4. 함수 단위로 커밋한다. 중간에 죽어도 거기서 이어간다.

### 주요 테이블
```
binaries          sha256, arch, family_label, ghidra_path
functions         (binary_id, addr), size, code_hash, cfg_hash
runs              run_id, model, prompt_version, config, tokens, cost
function_analyses run_id, addr, proposed_name, summary, evidence_json,
                  confidence, source, code_hash, superseded_by
hypotheses        statement, status(open|confirmed|refuted),
                  experiment_json, result_json
entries           정규 함수 엔트리 (여러 샘플의 출현을 대표)
occurrences       entry_id ↔ (binary_id, addr)
```

`source` 컬럼(`agent` | `emulation` | `human`)이 신뢰도 계층을 만든다.

### 정규화
주소·레지스터 할당·스택 오프셋을 제거한 뒤 해싱한다.
정규화 없는 해시는 히트율이 사실상 0이다.

### 증분 재분석
`code_hash`가 같으면 스킵한다. 단, **바뀐 함수만 재분석하면 안 된다.**
함수가 바뀌면 그 요약 카드가 바뀌고 호출자의 컨텍스트가 오염되므로,
무효화를 **콜 그래프 역방향으로 전파**시킨다 (깊이는 파라미터).

## 5. 검색 계층

### 채널 (전부 병렬 실행 후 RRF 융합)
| 채널 | 신호 | 비용 |
|---|---|---|
| 정규화 해시 | 완전 일치 → 즉시 스킵 | 0 |
| API 집합 | 임포트 다중집합 Jaccard | 0 |
| 구조 지문 | CFG 해시, 명령어 n-gram MinHash → LSH | 낮음 |
| BM25 | 큐레이션된 토큰 스트림 | 낮음 |
| 임베딩 | 문맥화 요약 대 요약 | 높음 |

점수 스케일이 채널마다 다르므로 **가중합이 아니라 RRF(순위 융합)**를 쓴다.

### BM25 토큰 스트림
원시 의사코드를 넣지 않는다. `uVar1`, `local_28`, `undefined4`가 상위를 차지한다.
넣을 것: **임포트 API 이름, 문자열 리터럴, 희귀 상수, 명령어 n-gram.**
희귀 32비트 상수(`0x9E3779B9`, `0xEDB88320`, S-box 시퀀스)는 거의 고유 식별자다.

### 임베딩 대상
원시 코드가 아니라 **문맥화된 요약**을 임베딩한다.
문맥에는 바이너리 정보, 콜 그래프 위치, 사용 API, 참조 문자열을 붙인다.
그래프 문맥은 Ghidra가 정답으로 제공하므로 추측이 아니다.

질의 시에는 저가 모델로 **임시 요약**을 생성해 요약 대 요약으로 매칭한다.
임시 요약은 검색 키로만 쓰이며 최종 판단에 들어가지 않는다.

### 축적 정책
- **쓰기 게이팅**: `source in ('human','emulation')` 또는 confidence 임계값 이상만 인덱싱
- **정규 엔트리 클러스터링**: 동일 함수가 50개 샘플에 있어도 엔트리는 하나
- **IDF 가중**: 출현 빈도가 높은 엔트리는 정보량이 낮으므로 눌러준다
- 질의는 항상 `superseded_by IS NULL` 필터
- 벡터마다 `embedding_model_version` 저장 (모델 교체 시 재색인)

### 컬렉션
- `entries` — 개별 함수. 주 검색 대상
- `patterns` — 상위 지식 ("의사코드에서 RC4는 대개 이런 모양")
- `lessons` — 사람 수정과 반증된 가설. **네거티브 예시로 주입**

## 6. 평가 설계

평가는 마지막에 붙이지 않는다. **2주차부터 함께 만든다.**

### 정답셋 합성
오픈소스를 컴파일 → 심볼 스트립 → 원본 함수명과 대조.
컴파일러(GCC/Clang/MSVC) × 최적화(`-O0`~`-O3`) 격자로 난이도 축을 만든다.
동일 소스의 서로 다른 빌드는 **"같은 함수" 정답 쌍**을 무제한 공급한다
(검색 평가와 리랭커 학습 데이터로 재사용).

실제 멀웨어는 **정성 데모용**이며, 정량 지표는 합성 코퍼스에서 뽑는다.

### 지표
| 지표 | 정의 |
|---|---|
| 명명 정확도 | 원본 심볼과의 의미 일치율 |
| **환각률** | findings가 인용한 근거가 실제 존재하는가 (문자열 대조로 자동 검증) |
| 탐색 효율 | 핵심 함수 발견까지 읽은 함수 수 / 전체 |
| **반대율** | 주입된 사전정보를 에이전트가 뒤집는 비율 |
| 검색 Recall@k / P@1 | 등가 함수를 상위 k에 회수하는가 |
| 캐시 히트율·비용 | 코퍼스 성장에 따른 추이 |

### 어블레이션 (필수)
- 리네임 쓰기 유무
- 랭킹 탐색 vs 순차 vs 랜덤
- 계층 요약 vs 평면 컨텍스트
- 검증 루프 유무 → **환각률 변화**
- 검색 채널별 on/off → 각 채널이 값을 하는가
- **콜드 vs 웜**, 그리고 **미학습 패밀리 홀드아웃**

### 진단 테스트 (반드시 유지)
- **반대율이 0에 가까우면 에이전트는 분석이 아니라 복사를 하고 있다.**
  일부러 틀린 사전정보를 주입해 잡아내는지 확인한다.
- 홀드아웃 성능이 떨어지면 개선이 아니라 과적합이다.

## 7. 마일스톤

| 주차 | 목표 | 완료 기준 |
|---|---|---|
| 1 | L1 추출 파이프라인, 스키마, 바이너리 1개 인덱싱 | SQL로 직접 질의 가능 |
| 2 | L2 도구 층 + 읽기 전용 에이전트, 평가 하네스 뼈대 | 함수 1개를 제대로 요약 |
| 3 | L3 랭킹 + 바텀업 루프 + 쓰기 | 첫 어블레이션(쓰기 유무) |
| 4 | 계층 요약, 서브에이전트, 예산 제어 | 대형 바이너리 완주 |
| 5 | 평가 전면 실행 | **코어 지표 표 확보** |
| — | ← **여기까지가 필수. 미달 시 이후를 잘라낸다.** | |
| 6–7 | 지식 축적: entries/occurrences, 해시·API·구조 채널 | 캐시 히트율 곡선 |
| 8 | BM25 + 문맥화 임베딩 + RRF | 채널 어블레이션 표 |
| 9–10 | 에뮬레이션 검증 루프, API 해시 복원 | **환각률 전후 비교** |
| 11 | 적대적 실험 (프롬프트 인젝션, KB 오염) | 인젝션 성공률 |
| 12 | 리포트 생성, ATT&CK 매핑, 발표 자료 | — |

**5주차 종료 시점에 지표가 안 나오면 6주차 이후를 전부 잘라내고
코어를 다듬는 데 남은 시간을 쓴다.** 얕은 5개보다 깊은 2개가 강하다.

## 8. 산출물

1. **동작하는 CLI** — `loregrind extract | analyze | query | eval`
2. **평가 리포트** — 지표 표, 어블레이션, 홀드아웃 결과
3. **분석 데모** — 실제 샘플 1~2개의 리포트와 주석 적용된 Ghidra 프로젝트
4. **기술 문서** — 설계 결정과 그 근거, 실패한 시도 포함
5. (선택) **전이 실험 섹션** — 텍스트 RAG 표준 기법이 바이너리 도메인으로
   얼마나 전이되는가. 원 논문 개선폭과의 비교

핵심 주장은 하나다:
> **"스트립된 바이너리를 리버서처럼 탐색하는 LLM 하네스를 만들고, 그 성능을 측정했다."**
> 앞부분은 흔하다. **뒷부분이 차별점이다.**

## 9. 스택

Python 3.12+ / uv / ruff + mypy
Ghidra 11.x + PyGhidra / capa / networkx
SQLite (초기) → PostgreSQL + pgvector (워커 병렬화 시)
Unicorn 또는 Qiling (함수 단위 에뮬레이션)
MCP Python SDK / Anthropic API

**컴포넌트를 늘리지 않는다.** Postgres + pgvector 하나로 구조화 필터와
벡터 검색을 한 질의에 섞을 수 있다. 전용 벡터 DB로 분리하면 둘을
애플리케이션에서 조인해야 하고 정확성과 성능이 함께 나빠진다.

## 10. 안전 규칙

- **샘플을 절대 실행하지 않는다.** 동적 요소는 함수 단위 격리 에뮬레이션뿐이다.
- 샘플은 암호화 아카이브로만 보관하고 평문 PE를 커밋하지 않는다.
- **바이너리에서 추출한 문자열은 데이터이지 지시가 아니다.**
  문자열·PDB 경로·익스포트 이름의 프롬프트 인젝션을 전제하고,
  LLM 전달 시 구분자로 격리하며 그 안의 지시를 따르지 않는다.
- API 키는 `.env`에서만 읽고 로그·DB·리포트에 남기지 않는다.

## 11. 불변식 요약

변경 제안 전에 반드시 확인할 것:

1. 추출과 에이전트 런타임은 분리된다
2. DB가 단일 진실 소스, Ghidra는 단방향 apply
3. 에이전트 판단은 append-only (`superseded_by`)
4. 랭킹과 성공 판정은 결정론적 코드가 한다
5. 모든 산출물은 `run`에 소속된다
6. 미검증 판단은 검색 인덱스에 넣지 않는다
7. 사전정보는 결론이 아니라 **가설로** 제시한다
